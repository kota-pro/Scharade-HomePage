## 確認された経路と対策

実会員の情報を取り出す試験、第三者への送信、悪意ある画像の本番実行は行っていない。攻撃想定の検証は架空の会員・画像・外部連携を使う。

| 経路 | 起き得る問題 | 対策 |
| --- | --- | --- |
| Git・エディタ保存履歴 | CMSキー、会員情報、パスワードハッシュ、過去のセッション情報を回収できる | `.env`・`.data`・`.history` の全履歴を除去し、旧キーを失効する。ハッシュが露出時と一致するアカウントを再設定必須にし、全旧セッションを失効する |
| 認証の総当たり | アカウント単位の試行を繰り返せる | 15分あたりアカウント5回・送信元20回を処理前に予約。成功時にアカウント枠を解放。期限付きで永久ロックを避ける |
| 再設定要求によるメール存在確認 | 応答内容・メール送信時間から登録済みアドレスを推測できる | 登録有無・配信失敗に共通の応答と最低応答時間を使い、配信を時間制限付きでバックグラウンド処理。未配信トークンを失効し、アドレスごとの要求も制限 |
| 新規登録によるメール存在確認・なりすまし申請 | 登録済みメールへの重複応答から所属を推測する、他人のアドレスで申請する | 登録前にメール所有確認を必須化。確認前は入力メールを会員データと照合せず同じ応答と最低600msを使用。6桁コードは10分・5回まで、コードはHMAC・トークンはSHA-256で保存。送信は15分にアドレス5回まで。コードは1回限りで、確認後の同時登録を直列化し、1アカウントだけ作成 |
| パスワードハッシュ解析 | 旧ハッシュの負荷設定が弱い | 非同期scrypt（N=32768/r=8/p=3）。新規・再設定は7文字以上で半角英大文字・半角英小文字・数字・記号を各1文字以上必須。露出した古いパスワードの再使用を拒否 |
| 運営のパスワード流出 | パスワードだけで管理操作できる | 運営・管理者は新しいブラウザー・明示ログアウト後・同じブラウザーの未利用7日後に、既存登録メールへの6桁コードで確認する。OAuthも同じ条件。一般会員には追加認証を要求しない |
| セッションファイル流出 | 保存された生のトークンでログインできる | ランダムトークンはCookieにだけ渡し、保存するのはSHA-256ハッシュ。HTTPSで`__Host-`、Secure、HttpOnly、SameSite=Lax、Domain指定なし |
| 運営セッションの放置 | 長期間の管理権限利用 | 全権限でKeep me signed in選択時30日、未選択8時間。運営・管理者は未利用7日でも失効する。期限5分前に延長を確認し、未応答なら失効する。権限・パスワード変更による失効を維持 |
| MFAコードの再利用・総当たり | 同じコードを再利用する、再送で試行制限を回避する | メールコードは1回限り・10分。アカウント単位で15分に誤入力5回、送信5回、再送60秒間隔。再送で期限や試行回数を延長・初期化しない。受信先・パスワード・認証バージョンに結び付ける |
| MFAデータの流出 | 保存されたコードや認証許可を回収する | コードは独立した64桁hex鍵によるHMAC、チャレンジ・1分の認証許可はSHA-256で保存。メール送信失敗は許可せず、認証許可は対象者・メール・パスワードに結び付けて1回だけ使用 |
| CMSの記事・リンク改ざん | JavaScriptや不正URLを埋め込める | 記事HTMLを許可リストで無害化、画像ホストとHTTPS URLを検証。CSPでインラインスクリプトは生成済みハッシュだけを許可 |

| 署名付きGAS送信の再送 | 正しい送信をコピーして副作用を繰り返せる | v2署名に128bit nonceを含め、Google側の永続プロパティと短時間のロックで10分間予約。業務IDは維持し、正当な再試行には新しいnonceを付ける |
| アカウント承認URLの転送 | 署名付きリンクを入手した人は承認・非承認の権限を持つ | 10月16日の所有者指示により、メールの署名付きリンクではログインを要求しない。HMACと7日の有効期限、確定POST・Origin検査を維持し、GETでは更新しない。最初の判断を記録し、古い承認／拒否リンクによる反転を拒否。リンクを承認権限として管理する。管理画面では引き続き管理者のメール二段階認証を必須とする |
| トークン付きURLのログ・Referer | 再設定・承認トークンが別サイトやログへ渡る | 対象画面はno-referrer/no-store/noindex。アクセスログからクエリを除外し、リクエストURLを含み得る通常のNginxエラーログを出さない |
| 共有キャッシュ | 会員向け応答を別の利用者へ渡す | 認証応答・API・HTML・転送・拒否応答はprivate/no-store、Nginx proxy_cacheを停止 |

## 依存ライブラリ

Astro 7.3.8、Node adapter 11.1.7、Sharp 0.35.5を使用。2026-10-29にNodemailer 10.3.0、sanitize-html 2.18.1へ更新し、間接依存のUndici 8.12.3・Zod 4.6.7を固定した。型検査用ライブラリは開発依存とし、yaml 2.9.1・source-map-js 1.2.2を維持し、型検査経路のfast-uriだけは3.1.9へ更新する。

初回の監査で残った`http-cache-semantics`のHigh警告（GHSA-ch52-4w7c-c8xp）は、10月28日に有効な脆弱性ではないとして撤回された。Cookieや認証ヘッダーを使う画像のビルド取得は行わず、会員HTML/API/写真の共有キャッシュも使わない。

10月29日の更新前はHigh 5・Moderate 8・Low 1。修正版で14件すべてが解消し、本番依存監査は0件となった。開発用のfast-uriにもModerate 2・Low 2があったため3.1.9へ更新し、開発・ビルド用を含む全依存監査も0件とした。閉じていないiframeの入れ子1500段で旧版がスタックオーバーフローになることと、メールアドレス中の入れ子コメントが別の宛先へ誤解釈されることを、架空データ・ネットワークを使わないメール生成だけで再現した。再発防止の検証は記事とPortfolioのHTML処理、および4種のメール宛先境界を対象とする。実会員へのメール送信や、細工したHTMLの本番実行は行わない。

新規登録の確認コードを送る段階では、登録済み・未登録で応答を分けない。配信はバックグラウンドで処理し、失敗したコードだけを失効する。再取得しても以前に届いた有効コードを一律失効させない。確認用トークンはURLやブラウザストレージに置かず、メモリから登録要求に渡す。登録済みの場合のログイン・再設定案内は所有確認後だけ表示する。SMTPが利用できない場合はメール所有確認を省略せず、新規申請を停止する。

## 秘密情報・外部サービスの切替

microCMSは所有者の指示により、無料のHobbyプランを維持し、再発行したサーバー専用1キーを`MICROCMS_SERVER_API_KEY`へ登録した。読み取り、Portfolio更新、Managementの各呼び出しはこの変数だけを参照し、旧`MICROCMS_API_KEY`や旧用途別変数へのフォールバックは行わない。変更前のキーと一致する場合は事前検証を拒否し、保存した旧キーのSHA-256指紋とも照合する。

| 設定 | 最小権限 |
| --- | --- |
| Content APIのデフォルト権限 | すべて無効。将来追加されるAPIにも自動で許可しない |
| blog / card_image の個別権限 | GETだけ |
| portfolio の個別権限 | GET / POST / PATCH / DELETEだけ。PUTは無効 |
| 下書き・公開終了コンテンツの全取得 | すべて無効 |
| Management API | メディアアップロードとコンテンツの取得（一覧・詳細）だけ。メディア削除・API作成・会員取得等は無効 |

所有者の管理画面でHobbyプランと登録済みキー1個を確認した。無料プランでは用途別の鍵分離ができず、サーバー専用キーが流出すると上記権限のすべてが影響を受ける。この制約を説明し、所有者からHobbyを維持する指示を受けた。Web・会計・写真展の3プロセスを停止し、本番データを保全した後に、所有者が旧キーを削除して新キーを作成した。新キーに上記権限を保存し、再読み込み後のContent API・Management API両方の設定を照合した。旧キーの401と、新キーの必要な読み取り4件の200・不要な管理API2件の403を確認した。キーをブラウザーへ送らず、Git・ログ・公開ビルドへ含めない。[microCMS公式の権限・個数の説明](https://document.microcms.io/content-api/x-microcms-api-key)。

Google Mapsはサイト専用の新しい公開キーへ切り替え、HTTP Refererを`https://scharade.jp/*`と`https://www.scharade.jp/*`に制限し、Maps JavaScript APIだけを許可した。所有者が新キーを作成し、設定を再読み込みして照合した後、本番へ切り替え、地図表示も確認した。旧Server keyと切替前のサイトキーの一致は値を出さず照合した。旧キーの直近7日間の利用記録にはMaps JavaScriptの成功（200）、Firebaseのパスワード方針取得の成功（200）、Dynamic Linksのエラー（400）、Geocodingの拒否（403）があった。要求元アプリは特定できず、Firebaseの個人データ取得を示す記録ではない。所有者の指示どおり旧キーの変更は保留しているため、そのキーが第三者に利用される可能性は残る。Nginxは地図ページ`/About_us`だけ参照元のドメインを送り、その他の画面やtoken・sig付きURLでは参照元を送らない。実際のNginxで6ケース、本番HTTPSで4ケースを確認した。[Google Maps公式のキー制限の説明](https://developers.google.com/maps/api-security-best-practices)。
