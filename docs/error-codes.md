# サイト全体のエラー番号対応表

利用者向けの同じ一覧は公開ページ `/Errors` にあります。フッターの「エラー番号の案内」から開けます。問い合わせ時は番号と操作していたページをお知らせください。

## 追加した修正計画

- 写真展の未添付写真とフォントの取得失敗を修正する。フォントは再取得可能にし、最大5秒の待機後はサーバーで印刷枠を検証して提出を続ける。
- 対象をサイト全体とし、認証・会員・管理・問い合わせ・写真展・Portfolio・公開ページのエラーを「番号＋利用者向けの説明」に統一する。ブラウザーが表示する必須項目・数値範囲の警告も対象とする。
- APIの失敗応答に `errorCode` を追加する。既存の機能別 `code` と詳細情報は保持する。成功応答・認証Cookie・HTTP状態・アクセス制限は維持する。
- エラー通知と画面内のエラー欄を共通処理で整える。既存のリンク・操作ボタンを保持し、進行中や成功の案内、一般の記事本文には番号を付けない。
- 内部の識別番号・JSON・ブラウザーの英語例外は画面に出さず、必要な操作へ置き換える。保存・送信結果が不明な場合は、重複送信を避けて状態を確認する案内を保つ。
- 対応表を文書と公開ページに用意し、単体テストと3ブラウザーで番号・案内・入力保持・通常動作を検証する。

共通処理は `src/lib/siteErrors.ts` の登録表を使用します。サーバーで通常のJSON応答と早期の拒否応答に番号を付け、画面では通知・エラー欄・後から開くダイアログを整えます。通信の成功応答や共同編集のイベント配信を書き換えません。ブラウザーが動作しない場合も、404・503ページとテキスト形式の拒否応答には番号を表示します。

## エラーレポートの自動送信

本番ではエラーを `contact@scharade.jp` へ自動報告します。既存の `GMAIL_PASS` とメール送信処理を使用し、送信先をブラウザーやフォームから変更することはできません。開発環境では既定で送信しません。`SITE_ERROR_REPORTS_ENABLED=0` で停止、`1` で明示的に有効化できます。設定変更後はWebプロセスを再起動してください。

- 対象：サーバーの5xx障害、API応答の破損、サイト内スクリプトのプログラム例外、フォント配信のHTTPエラー・破損、登録済みのサイト設定不備。エラー欄が表示されたこと自体を送信理由にはしません。
- 対象外：入力間違い、認証情報の不一致、ログイン期限切れ、権限不足、受付期間外、通常の404、競合、添付条件違反、回数制限、オフライン、通信の中断、端末の文字計測機能の制約。旧バージョンが保存した送信待ちにも新しい条件を適用します。
- 本文：固定のエラー番号と説明、発生・受信日時（日本時間）、ページや処理の種類、HTTP状態、ブラウザー・端末の種類、接続状態、フォント取得の失敗の種類など。サーバー例外は入力内容を含まないソース位置だけを補足します。
- 含めない情報：入力本文・氏名・メールアドレス・写真・ファイル名・パスワード・確認コード・Cookie・IPアドレス・完全なUser-Agent・URLのクエリーやフラグメント・動的な識別情報。実際の画面の文章や例外メッセージをそのまま送信しません。
- 重複抑制：同じ番号・機能は10分間追加メールを抑制します。APIと画面で同じエラーを検出しても一つにまとめます。フォントは失敗の種類とRegular/Boldも区別します。後続の回数はサイト内の記録に加算し、既に送ったメールは更新しません。
- 送信制限：全体で1時間20回のSMTP送信試行まで。上限を超えたレポートは送信待ちに残します。
- 障害時：メール送信はフォームやAPI応答と切り離します。送信失敗は1分から最大1時間の間隔で再試行し、再起動後も送信待ちを引き継ぎます。レポート送信自体の失敗は再報告せず、無限ループを防ぎます。
- ブラウザーがオフラインの間は、安全な診断項目だけを同じタブの一時保存に保持し、接続復帰・再読み込み後に再送します。本文や画像を一時保存へ追加することはありません。
- 保存先：`DATA_DIR/site-error-reports.json`。最大200件、未送信は最大7日、送信済みは24時間を目安に定期削除します。ブラウザー側は最大20件・24時間です。メールボックス内の通知は障害調査に使用します。

`EXH-022` はサイト側のフォント配信HTTPエラーとフォントの破損を報告します。端末のオフライン・通信失敗・時間切れ・文字計測機能の制約だけでは報告しません。端末で文字を計測できなくても、既存のサーバー検証による提出は継続できます。

APIのエラー本文には番号を付けて返し、`errorCode` と `X-Error-Code` に同じ番号を設定します。既存の処理識別用 `code` は維持します。HTTP状態の判定を文面より優先し、429のログイン制限をログイン切れ、503の認証メール障害を確認コード間違いとして扱わないようにします。写真展の例外に付いた専用番号は各APIで保持し、画面で付け替えません。

通知対象の障害説明は共通の公開定型文を画面とメールで使用します。復旧手順が必要な設定不備・承認後の通知失敗は、コードと対応する登録済みの説明IDだけを受け渡します。任意の画面文言・利用者の入力・外部サービスの生のメッセージはメールへ送信しません。

Webプロセスが30秒ごとに送信待ちを確認するため、新しいワーカーや外部メールサービスの契約は不要です。SMTPへの受理確認後に送信済みとし、受信箱への到着確認とは区別します。

標準のブラウザ検証では合成データ用サーバーと模擬SMTPを使用し、検証用メールをローカルの一時ファイルに記録します。

## Error Codeページと検索

案内ページの見出しは `Error Code`、フッターのリンクは `Error Code List` です。フッターのリンクはログイン中だけ表示し、PC・スマートフォンともDisclaimerの横へ配置します。案内ページ自体は従来どおり公開し、ログインできない場合の参照先としても利用できます。

コードまたは説明文の言葉で一覧を絞り込めます。英字の大文字・小文字、全角の英数字に対応し、コードのハイフンを省略した検索もできます。複数の言葉をスペースで区切ると、すべてを含む項目へ絞り込みます。「クリア」で全件を再表示します。検索文字列はURLやサーバーへ送らず、一致する項目がない場合もエラーレポートは発生しません。
